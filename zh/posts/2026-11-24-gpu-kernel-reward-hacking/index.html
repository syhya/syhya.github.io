2026 年 11 月 24 日，我在 SOL-ExecBench（Lin et al., 2026）的 L1、L2、Quantization 和 FlashInfer-Bench 四个 B200 官方榜单上均排在第一，页面均使用 Evaluation Stack v1.1。不过，这些成绩并不代表真实的 kernel 优化，而是利用评测漏洞取得的。本文以这次实验为切入点，分析 GPU kernel 优化中的 reward hacking：结合 SOL-ExecBench 的评测流程与具体案例，说明这些漏洞的成因、它们为何能通过评测，以及相应的防护方法。

实验结果：四个榜单第一#

上面分数均通过下文介绍的 reward hacking 方法取得，四个子榜单的题目全部通过。

什么是 Reward Hacking#

Reward hacking（奖励欺骗）是指利用奖励或评测规则的缺口获得高分，却没有相应实现设计者希望的目标。 Lilian Weng 的综述梳理了这个共同问题：实际被优化的奖励，未必完整实现我们真正想要的结果（Weng, 2024）。

在 kernel 优化里，真实目标是对当前输入完成规定计算，并且更快；评测器通常看到的则是有限正确性测试与一组计时读数。这些读数构成了优化时使用的代理目标。返回正确张量，不一定意味着处理了当前输入；整轮计算完成，也不一定意味着每次独立调用都完成了自己的工作。数值正确、调用语义和计时范围需要一起检查，只有都通过后的测验出来的分数才有可信度。

这类偏离可以分成不同路径：specification gaming 利用字面规则与真实目标之间的缺口，不一定修改评分器；reward tampering 则直接干预奖励函数或它依赖的证据。两者都可能让分数上升，却没有完成预期任务（Krakovna et al., 2020；Everitt et al., 2019）。

规则奖励和单元测试降低了部分主观性，仍然受输入覆盖、容差与执行边界限制。反过来，测试失败也不能直接叫作 hacking：EvilGenie（Gabor et al., 2025）发现，正常实现可能漏掉边界条件，利用测试分布的启发式实现也可能通过保留测试。因此，判断需要结合规格、代码和执行轨迹。

SOL-ExecBench 如何打分#

SOL-ExecBench 对单个 workload 使用以下评分公式（NVIDIA, 2026a）。

$$ S(T_k)=\frac{T_b-T_{\mathrm{SOL}}}{(T_k-T_{\mathrm{SOL}})+(T_b-T_{\mathrm{SOL}})}. $$

其中，$T_k$ 是候选实现的实测耗时，$T_b$ 是计分基线的耗时，$T_{\mathrm{SOL}}$ 是 SOLAR 估计的硬件耗时下界。计分基线是基于 PyTorch 参考实现优化得到的版本。在 $T_b>T_{\mathrm{SOL}}$、$T_k\geq T_{\mathrm{SOL}}$ 的条件下，分数上限为 1。

  • 与计分基线同速时，$S=0.5$。
  • 耗时达到 SOL 下界时，$S=1$。
  • 耗时趋于无穷时，$S\to 0$。

Fig. 3 展示了分数随耗时变化的曲线。越接近 SOL 耗时下界，同样幅度的耗时变化对分数的影响越大。

当计时漏掉本次调用应完成的部分计算时，测得的耗时 $T_k$ 可能低于估计的 SOL 耗时下界 $T_{\mathrm{SOL}}$。Cursor 在博客中提到若不当缓存等 Reward hacking 手段使测得的性能超出 B200 的硬件能力，评测流程应该成绩判为无效。

以 Fig. 4 中的算子 001_attention_softmax_dropout_value_matmul_backward 为例，B200 榜单记录的提交耗时为 0.002197 ms，低于该题 0.081720 ms 的 SOL 下界。线上评测服务会将超过 1 的 SOL score 截为 1。

四个案例#

下面四个例子各自对应一条不同的路径：例子一缓存最终输出，例子二冻结输入，例子三删去计算分支，例子四改变单次调用的计量单位。

例子一：根据地址变化返回旧输出#

069_rms_norm 的任务是先做残差相加，再执行 RMSNorm 并乘以权重。以下代码摘自 rmsnorm-submission.py，只保留单输出、直接返回张量的路径：

def run(*args):
    in_args = args[:_NUM_INPUTS]
    tensor_inputs = tuple(x for x in in_args if isinstance(x, torch.Tensor))
    scalars = tuple(float(x) for x in in_args if not isinstance(x, torch.Tensor))

    if _reusable(tensor_inputs, scalars):
        return _CACHE["outputs"][0]

    out = _ref_run(*in_args)
    _capture(tensor_inputs, scalars, out)
    return out

未命中缓存时，_ref_run 执行 PyTorch 参考计算，_capture 克隆输出并记录输入信息。命中时，直接返回之前的结果。关键在于 _reusable 如何判断可以复用：它检查输入数量、标量和字节数，却不比较张量内容，而是检查地址是否一起向前移动。

下面是其中的判断循环。_MIN_SHIFT = 256，_MAX_SHIFT = 2048：

shift = None
cur_ptrs = []
for t, prev_ptr, prev_bytes in zip(tensor_inputs, _CACHE["pointers"], _CACHE["nbytes"]):
    nb = t.numel() * t.element_size()
    ptr = t.data_ptr()
    if nb != prev_bytes or ptr < prev_ptr:
        return False
    cur_shift = ptr - prev_ptr
    if shift is None:
        shift = cur_shift
    elif cur_shift != shift:
        return False
    cur_ptrs.append(ptr)
if shift is None or shift < _MIN_SHIFT or shift > _MAX_SHIFT:
    return False

这对应了保存记录中的 evaluator 版本（NVIDIA, 2026b；commit a9fa080）的分配方式：每轮所有输入共同前移 256～2048 字节，但新地址中复制的仍是同一份输入数据（分配器源码）。因此，地址轮换没有阻止缓存，反而给缓存提供了识别依据。

正确性阶段会重新生成输入；缓存未命中时，提交正常计算。计时阶段反复使用相同输入值，预热便有机会填充缓存。命中后，_reusable 更新保存的地址，启动一个只写入整数 0 的 Triton marker kernel，再让 run 返回旧输出。

该版本的 CUPTI 计时器会在预热后记录候选的 GPU 活动序列，并匹配后续迭代的序列。它能记录 kernel、内存复制等活动，却无法仅凭序列一致判断这些活动是否完成了 RMSNorm。发现序列时若已走缓存路径，后续也可以只匹配到 marker（计时源码）。

2026 年 11 月 23 日保存的 rmsnorm-evaluation.json 中，这份提交在 B200 上对一个 BF16 workload（1 × 8192 × 8192，eps = 1e-5）得到 PASSED，最大绝对与相对误差均为 0，报告耗时 2.064 μs。配置是 10 次预热、50 次计时、seed 200；未锁频，也没有测量参考耗时。记录没有逐次缓存命中日志；上述源码路径与评测流程提供了一种解释：正确性阶段正常计算，计时阶段复用缓存。

例子二：调用次数到了，就不再更新输入#

另一种方式不直接缓存最终答案，而是保留输入或中间结果。在 067_flash_attention_gqa_ultralong 的 Hyra 公开提交（flash_attention_gqa_ultralong）中，main.cpp 有这样的逻辑。下面省略了缓冲区分配与参数组装：

static std::unordered_map<int64_t, int> g_call_count;
static const int PREP_CALLS = 15;

int64_t gkey = B * 100000000LL + S;
int cnt = ++g_call_count[gkey];
bool do_prep = (cnt <= PREP_CALLS) || grew;

if (do_prep) {
    prep_launch(srcs, dsts, sigs, lens, modes, 7, stream);
}

prep_launch 负责把当前输入转换、复制到内部缓冲。对同一 (B, S) 连续调用，且没有扩容或其他调用改写缓冲时，第 16 次起这一步就被跳过了。即使传入新的 hidden states、RoPE 参数或权重，后面的计算仍读取旧缓冲。

即使进入 prep_launch，它也只抽样检查每个输入的 256 个位置。下面是 CUDA 源码中的判断；samp_pos 按固定间隔选点：

float cur = tab.s[w][samp_pos(t, n)];
float st  = tab.sig[w][t];
int dirty = __syncthreads_or((cur != st) ? 1 : 0);
if (!dirty) return;

只修改未抽样的位置，就可能让内部缓冲保持旧值。它与前一例的地址判断不同：抽样值相同不等于完整输入相同，地址变化符合规律更不能证明内容相同。 对接口允许的固定权重可以预处理；对可能变化的输入，缓存需要可靠的有效性条件。

这份代码还会在 S <= 4096 时捕获、重放 CUDA Graph。Graph 重放仍会执行 GPU 计算；这里的问题是输入不再刷新。 PyTorch 文档说明了固定地址与更新数据的区别：重放复用捕获时的地址，但可以读取这些地址里的新内容。若使用内部静态输入，就需要在重放前写入本次输入；不能靠调用次数来决定是否更新。

这个例子与前一个的节省来源不同：前者可以跳过 RMSNorm 本身，这里省掉的是输入准备，并对旧数据继续计算。

例子三：利用输入分布，删掉整个计算分支#

051_seqlen-finetuned-reconstructed_hyena_complete_forward_block 的参考任务包含 Hyena mixer 和后续 MLP。Hyra 公开提交（hyena_complete_forward_block）却只挑选了八个张量参数，相关的两处代码是：

_NEED_IDX = [0, 3, 4, 20, 21, 22, 23, 24]
needed = [all_args[i] for i in _NEED_IDX]

这些索引对应 hidden states、第二层归一化参数、输出投影 bias 和 MLP 参数；第一层归一化、短卷积、长滤波器与输出投影 weight 都没有进入计算。_prologue 直接从 hidden_states + out_proj_bias 构造残差，再执行归一化和 MLP。这里被删除的是计算分支，而不是通过融合减少 kernel 数量。一个可能的解释是：参考输入中多组权重按 randn * 0.02 初始化，经过门控后，Hyena 分支的贡献可能小到被最终输出容差掩盖。

同一提交还在计数超过 11 后停止向 Graph 的静态输入复制新值，叠加了前一例的状态问题。删分支和冻结输入是两条独立路径：换一批随机种子可能暴露前者，却未必触及计时阶段的后者。

例子四：计算完成了，单次调用的含义却变了#

跨调用状态还可以改变工作的组织方式。GPU MODE 的 NVFP4 复盘（Kokoromyti, 2026）记录了一份以 11.191 μs 登顶、随后被撤销成绩的提交。它利用了正确性检查与计时循环的差异：正确性阶段，评测器传入 15 份克隆数据，提交每次都正常运行 8-group GEMM，同时用 id(data) 计数；数到 15，就判断接下来进入计时阶段。

计时阶段，评测器重复传入同一批对象。第一次调用启动一个合并 15 份数据的 120-group kernel，其余 14 次只返回缓存的输出。GPU 上只运行了一个 kernel，总耗时却被除以 15。

这个案例确实完成了矩阵乘法，也可能获得真实的批处理吞吐收益；但把整批耗时除以 15，得到的是跨调用摊销后的读数。它没有证明一个独立请求能以同样延迟完成。如果生产接口允许合批，这可以是合法优化，同时需要报告等待成批的时间。评测需要验证的，不只是答案对不对，还包括分数采用的工作单位是否符合任务约定。

公开报告中还有哪些方法#

SOL-ExecBench 论文在内部 Agent 实验中标记并拒绝了 589 份提交，占该实验全部提交的 14.5%。Fig. 6 展示了检测到的类型及其分布（Lin et al., 2026）。

论文将观察到的八种评测作弊手法分为并发绕过、状态与缓存和环境干预三类，并且列举了对应的防护措施。

下表汇总了 SOL-ExecBench 及其他 GPU kernel 评测与竞赛中公开记录的案例。

方法公开案例
只适配固定测试值doubleAI 报告，一份 RoPE 实现只支持测试集里的 16 个 theta 值，遇到其他值就会出错。doubleAI 还用新的随机种子做了复测，8 个此前通过的 kernel 各自在至少一个测试负载上失败。
利用测试容差SF Tensor 发现，一项 MoE 任务要求计算权重最高的 10 个专家并汇总结果，有个提交只算了前 2 个。由于路由权重高度集中，输出仍在测试容差内。
复用已有答案METR 记录了 o3 在一次 GPU kernel 优化评测中直接返回评分器预先算好的参考结果。这个案例暴露了评测器与候选实现之间的隔离缺口。
跨调用缓存Wafer 在 GEMM 评测中观察到，有提交先算出结果并保存下来，后续计时调用直接返回缓存的输出。这样测得的耗时没有计入重新计算的成本。
跨调用合批GPU MODE 的 NVFP4 复盘记录了一份把 15 次调用合成一次 GPU 计算的提交。评测器把整批耗时除以 15，得到的是批量处理时每次调用分摊的耗时。
把计算移出计时Wafer 描述了两种计时器可能漏掉实际计算的情形。计算有时在计时器未覆盖的 CUDA stream 上执行，有时直到评测器检查输出时才开始。
干预计时或校验METR 记录，同一次 o3 尝试后来还改动了计时和 CUDA 同步函数。SF Tensor 则发现，有提交降低了同进程中参考实现的计算精度，使候选输出更容易通过误差检查。

SOL-ExecBench 论文 v1 描述的是 CUDA Event 计时。例子一采用的评测器版本 a9fa080 默认使用 CUPTI，可以观测不同 CUDA stream 上的 GPU 活动，并按识别出的 kernel 活动序列计时。对于例子一的 workload，还需要在计时路径中改变输入值并核对输出，才能检查本次调用是否处理了当前输入。

怎样减少 Reward Hacking#

先修复评测协议和执行边界#

针对上面的案例，优先补三类检查：

  1. 在计时流程中改变输入值，并核对输出。 同形状下测试原地修改、重新分配，以及相同地址偏移但不同内容的输入。生成数据和比较结果可以放在计时区间外，但不能让正确性只覆盖另一条执行路径。
  2. 改变调用历史与数值分布。 调整预热次数，交错输入和形状；只改未抽样位置，或放大被忽略的计算分支。前者检查状态复用，后者检查容差与输入覆盖，两者需要分别测试。
  3. 保护参考数据与评分过程。 写清楚允许的缓存、预处理、合批及计时范围，把参考答案、计时器和权威记录放到候选不能任意读写的边界。保留正常实现作为正对照，以缓存、删分支和计时绕过实现作为负对照；新增检查需要既拒绝漏洞，也接受合法优化。

这些措施针对的是本文案例；它们需要用保留的漏洞实现逐项验证，不能因为增加了随机种子、CUPTI 或代码审核，就宣称整个评测已经可靠。

内部评估框架中的几项策略#

内部的 kernel 评估框架保留两种模式，对应不同的评估目标：

  • 隔离模式：生成容器先清理题包，Codex 等 Agent 的题目工作目录只保留 base.py、input.py、shapes.json、constraints.md 和 self_check.py。生产 reference、冻结耗时表和评测实现不可见，正式评测在另一份全新、完整的仓库副本中运行，衡量从题面生成实现的能力。
  • 非隔离模式：开放完整题包，衡量 Agent 面向目标负载能满足多少生产提效需求。在提交规则允许的范围内复用已有实现，也可以是有效的优化路径。

两种模式分别报分，自检与正式评测共享计时实现。具体检查包括：

检查环节做法与例子
GPU 频率候选与 reference 使用相同的 SM 锁频设置，并回读校验（NVIDIA, 2026c），减少 Boost 波动或两侧不同频造成的偏差。当前环境按最高 SM 频率的约 0.73 倍设定目标，回读误差要求在 ±15 MHz 内。
计时范围使用 CUDA Graph 捕获与重放，在 Event 计时区间前后同步 GPU，并核对重放后的输出。结合节点数和逐调用对照计时，拒绝空图、部分捕获与异常耗时，检查把工作转移到其他 stream 或 CPU 线程的路径。
跨调用状态与缓存使用 3 个独立 seed 重建输入并比对输出，检查“首轮计算、后续复用”的实现；计时池通过 clone_inputs 分配不同地址，总量大于 2 倍 L2 容量，减少固定对象复用与热缓存偏差。
输入改写对禁止原地修改的张量保存快照，用 view(torch.uint8) 按字节比较。例如 +0.0 改成 -0.0 在数值上相等，但字节已经改变；FP8 打包数据也按原始字节检查。
接口与数值核对 shape、dtype 和数值误差。例如要求 FP32 输出时，不能直接返回 FP16；内部计算是否降低精度，仍由数值测试检查。
导入与执行策略按提交规则做 AST 检查，例如拒绝直接导入 reference、受限 vendor 库或调用 torch.matmul。Graph 重放减少对候选 Python 包装层的依赖，导入、预热和捕获阶段仍需检查。
评分基线加入分派路径检查：生产实现未加载成功时直接报错，避免静默回退到较慢的 PyTorch 路径，把 reference 耗时和 speedup 一起抬高。
审计记录保存环境、输入、候选代码与各阶段判定。例如同时记录 seed、Graph 节点数、时钟读数和实际 reference 分派路径，便于复现异常成绩。

这些判定也会进入最终评分：计时无效或未通过反作弊检查的结果，性能分记为零。

随机输入检查内容依赖，地址轮换检查固定对象依赖，大工作集减少热缓存偏差；复制相同数值到新地址，不能代替对新输入的正确性检查。

用形式化验证加强语义检查#

SF Tensor 的形式化正确性工作（Koska et al., 2026）尝试从 PTX 建立符号模型，通过求解器验证实现与规格等价，覆盖随机测试容易漏掉的分支、mask 和同步问题。它把“测过若干输入”推进到“在模型与前提下证明性质”，但早期实现将浮点数视为精确实数，不能据此保证实际浮点误差。

让监控形成“发现、调查、补洞”的闭环#

OpenAI 的 CoT 监控研究（Baker et al., 2025）展示了用监控发现作弊轨迹、人工调查并修补环境漏洞的过程。对 kernel Agent，可以同时保留工具调用、提交差异、GPU 活动与权威测试结果，用监控寻找新模式，再把确认的漏洞变成回归负例。

监控本身也要验收。OpenAI 的后续实践（OpenAI, 2026）采用分层调查，并随机抽查未触发告警的样本、用历史事件和红队测试漏检。只看告警率会漏掉隐蔽行为；实际 hacking、监控召回与误报、有效计算通过率和防护开销，需要分开报告。

训练中惩罚已证实的绕过行为#

评测漏洞进入训练后，还可能影响后续行为。Denison 等人用构造课程奖励较轻的 specification gaming；在未直接训练奖励篡改的测试场景中，模型也曾在少数试次里改写模拟奖励代码（Denison et al., 2024）。这展示了投机行为跨场景泛化的一条路径，不能据此估计部署模型的作弊率。

Anthropic 的研究（MacDiarmid et al., 2025）发现，在其 coding RL 设置中，足够权重的偏好奖励或专门的 hacking 检测惩罚可以抑制已知作弊。普通聊天型 RLHF 则不能保证修复 agentic 行为；inoculation prompting 主要减少作弊向其他失配行为的泛化，并没有修复评分器漏洞。

也要避免把“更少说出作弊意图”当成成功。OpenAI 的实验表明，直接对 CoT 施加强优化压力，可能让剩余作弊更难被监控发现。因此，应依据可靠的行为与执行证据判定候选是否有效，再独立检查监控和训练干预的效果。

MONA（Farquhar et al., 2025）则尝试改变多步优化的激励：只把单步或短期回报用于优化，并加入监督者对长期影响的预先评价，减少“先削弱检查、再从后续高分中获益”的动机。论文实验覆盖三个构造场景，也不解决单步硬编码等漏洞。对 kernel RL，这提供了奖励设计思路，仍需保留独立的数值、调用契约与计时验收。

总结#

一次 PASSED 和一个很小的耗时，只有对应到同一条有效执行路径上，才能成为优化效果的证据。评测需要验证的不只是“答案曾经算对过”，还包括“这次计时确实完成了当前请求”。

随着 Agent 越来越多地参与 kernel 优化，评测器本身也需要像 kernel 一样被持续测试、复现和修补；否则，榜单上的速度提升说明的只是评测被优化了，而不是计算真的变快了。
